# Unit: u09 | 9. Users and groups | Manage users and groups

Every process and every file on Linux belongs to a user and a group. This unit shows where accounts are stored, how to create, change and remove users and groups, how passwords and password aging work, and how to give people administrator rights without sharing the root password.

## Lesson: l0901 | Accounts and the files behind them

A user account is a name plus a number, the UID (user ID). The kernel only cares about the number; the name is for people. Root is always UID 0. On RHEL 9, accounts for services (sshd, chrony, apache...) get UIDs below 1000, and people get UIDs from 1000 up.

Local accounts live in four plain text files:

- `/etc/passwd`: one line per user, readable by everybody. Seven fields separated by colons: name, x (the password is elsewhere), UID, GID of the primary group, a comment (often the full name), the home folder and the login shell.
- `/etc/shadow`: the password hashes and the password aging numbers. Only root can read it.
- `/etc/group`: one line per group: name, x, GID and the list of extra members.
- `/etc/gshadow`: group passwords and group administrators (rarely used).

```terminal
[root@server1 ~]# grep student /etc/passwd /etc/group
/etc/passwd:student:x:1000:1000:Student:/home/student:/bin/bash
/etc/group:wheel:x:10:student
/etc/group:student:x:1000:
```

The student line reads: user student, UID 1000, primary group 1000, comment Student, home /home/student, shell /bin/bash. The group file shows two things: the group student (GID 1000) with no extra members, and the group wheel, which lists student as a member.

### Primary and secondary groups

Each user has exactly one primary group (the GID in /etc/passwd). New files the user creates belong to it. A user can also be a member of any number of secondary (supplementary) groups; those are the member lists in /etc/group. On RHEL each new user gets a private primary group with the same name.

```terminal
[root@server1 ~]# id student
uid=1000(student) gid=1000(student) groups=1000(student),10(wheel)
[root@server1 ~]# getent passwd student
student:x:1000:1000:Student:/home/student:/bin/bash
```

- `id USER` shows the UID, the primary group and all groups. `id -nG USER` lists only the group names.
- `getent passwd NAME` and `getent group NAME` ask the system's account database, so they also find accounts that come from a directory server, not just the local files. They print nothing (and fail) when the name does not exist, which makes them good for checks.

> Do not edit /etc/passwd or /etc/shadow by hand on the exam. Use the commands in the next lessons: they lock the files, keep both files in step and check what you type. If you really must edit, use `vipw` and `vipw -s`.

## Lesson: l0902 | Creating, changing and removing users

`useradd NAME` creates a user with the defaults: the next free UID from 1000 up, a private group of the same name, the home folder /home/NAME (a copy of /etc/skel), and the shell /bin/bash. The defaults come from /etc/login.defs and /etc/default/useradd (`useradd -D` shows them).

The options you need most:

- `-u UID`: a specific UID.
- `-g GROUP`: the primary group (the group must exist).
- `-G G1,G2`: secondary groups.
- `-c "TEXT"`: the comment field, usually the full name.
- `-d DIR`: a different home folder. `-m` creates it (the default on RHEL), `-M` creates no home folder.
- `-s SHELL`: the login shell, for example /sbin/nologin for an account that must not log in.
- `-e YYYY-MM-DD`: the day the account expires.

```terminal
[root@server1 ~]# useradd -u 2001 -c "Ana Lima" -s /bin/bash -m ana
[root@server1 ~]# id ana
uid=2001(ana) gid=2001(ana) groups=2001(ana)
[root@server1 ~]# getent passwd ana
ana:x:2001:2001:Ana Lima:/home/ana:/bin/bash
[root@server1 ~]# useradd -d /srv/bob -m bob
[root@server1 ~]# ls -ld /srv/bob
drwx------. 2 bob bob 60 Mar  2 04:00 /srv/bob
```

### Changing a user: usermod

`usermod` takes mostly the same options as useradd and changes an existing account:

- `usermod -s /sbin/nologin ana` changes the shell.
- `usermod -c "Ana M. Lima" ana` changes the comment.
- `usermod -aG devs ana` adds ana to the group devs and keeps her other groups.
- `usermod -d /home/ana2 -m ana` moves the home folder (without -m only the entry changes).
- `usermod -u 3001 ana` changes the UID (files in the home folder are updated, files elsewhere are not).
- `usermod -l newname oldname` renames the account.
- `usermod -e 2026-12-31 ana` sets the expiry date.

> The classic trap: `usermod -G devs ana` without -a REPLACES all of ana's secondary groups with devs. Always write `-aG` when the task says "add".

### Removing a user: userdel

`userdel NAME` removes the account but leaves the home folder and the mail spool behind. `userdel -r NAME` removes them too. Files left behind still carry the old UID, so `ls -l` shows a number instead of a name:

```terminal
[root@server1 ~]# userdel bob
[root@server1 ~]# ls -ld /srv/bob
drwx------. 2 2002 2002 60 Mar  2 04:00 /srv/bob
[root@server1 ~]# userdel -r ana
[root@server1 ~]# ls /home
student
```

If a new user later gets the same UID, that user owns the old files. `find / -nouser` lists files whose owner no longer exists.

## Lesson: l0903 | Groups and memberships

Groups let several users share files and rights. The group commands mirror the user commands:

- `groupadd NAME` creates a group with the next free GID from 1000 up; `groupadd -g 3000 NAME` picks the GID; `groupadd -r NAME` makes a system group (GID below 1000).
- `groupmod -n NEW OLD` renames a group; `groupmod -g GID NAME` changes its number.
- `groupdel NAME` removes a group. It refuses to remove a group that is some user's primary group.

```terminal
[root@server1 ~]# groupadd -g 3000 devs
[root@server1 ~]# usermod -aG devs ana
[root@server1 ~]# id ana
uid=2001(ana) gid=2001(ana) groups=2001(ana),3000(devs)
[root@server1 ~]# groups ana
ana : ana devs
[root@server1 ~]# groupmod -n developers devs
[root@server1 ~]# groupmod -g 3100 developers
[root@server1 ~]# getent group developers
developers:x:3100:ana
```

### Managing members with gpasswd

`gpasswd` edits a group's member list directly:

- `gpasswd -a USER GROUP` adds one user.
- `gpasswd -d USER GROUP` removes one user.
- `gpasswd -M u1,u2 GROUP` sets the whole member list at once.

```terminal
[root@server1 ~]# gpasswd -a bob developers
Adding user bob to group developers
[root@server1 ~]# gpasswd -d bob developers
Removing user bob from group developers
```

> A user who is logged in does not see a new group until the next login: group membership is read when the session starts. `id USER` reads the files and shows the new group at once; `id` with no name shows your current session.

## Lesson: l0904 | Passwords, password aging and locked accounts

Root sets anyone's password with `passwd USER` (it asks twice). A user changes their own password with `passwd` alone and must type the old one first. For scripts and for many users at once, two commands read the password from standard input:

```terminal
[root@server1 ~]# echo 'S3cret!pw' | passwd --stdin ana
Changing password for user ana.
passwd: all authentication tokens updated successfully.
[root@server1 ~]# echo 'maria:N3wer!pw' | chpasswd
```

`passwd --stdin` is a RHEL extension; `chpasswd` reads `user:password` lines and works everywhere. Put the password in single quotes so the shell does not touch characters like ! or $.

### Password aging

/etc/shadow keeps, for every user, the day of the last password change and four limits. `chage -l USER` shows them in plain words, and chage changes them:

- `chage -M 90 USER`: the password must be changed every 90 days (maximum age).
- `chage -m 7 USER`: the password can be changed at most once every 7 days (minimum age).
- `chage -W 10 USER`: warn 10 days before the password expires.
- `chage -I 5 USER`: after the password expired, the account still accepts a change for 5 days, then it is disabled (inactive).
- `chage -d 0 USER`: the password counts as expired, so the user must choose a new one at the next login.
- `chage -E 2026-12-31 USER`: the whole account expires on that day (`-E -1` removes the date).

```terminal
[root@server1 ~]# chage -M 90 -m 7 -W 10 ana
[root@server1 ~]# chage -l ana
Last password change					: Mar 02, 2026
Password expires					: May 31, 2026
Password inactive					: never
Account expires						: never
Minimum number of days between password change		: 7
Maximum number of days between password change		: 90
Number of days of warning before password expires	: 10
```

`passwd -x`, `-n`, `-w`, `-i` and `-e` do the same as chage -M, -m, -W, -I and -d 0, if you prefer passwd.

### Defaults for new users: /etc/login.defs

chage changes existing users. The values new users get come from /etc/login.defs:

```terminal
[root@server1 ~]# grep -E '^PASS_' /etc/login.defs
PASS_MAX_DAYS	99999
PASS_MIN_DAYS	0
PASS_WARN_AGE	7
```

Change PASS_MAX_DAYS to 60 and every user created afterwards must change the password every 60 days. Users that exist already keep their values: a task such as "all new users" means login.defs, "the user X" means chage.

### Locking accounts and nologin

- `passwd -l USER` (or `usermod -L USER`) locks the password: `!!` (passwd) or `!` (usermod) goes in front of the hash, so no password can match. `passwd -u` / `usermod -U` unlock it. Key-based ssh logins may still work while the password is locked.
- `usermod -e 1 USER` or `chage -E 0 USER` expires the whole account, which stops every kind of login.
- The shell /sbin/nologin refuses interactive logins. It suits accounts that only own files or run a service, or users who may only use a service such as file shares.

```terminal
[root@server1 ~]# passwd -l ana
Locking password for user ana.
passwd: Success
[root@server1 ~]# passwd -u ana
Unlocking password for user ana.
passwd: Success
[root@server1 ~]# useradd -s /sbin/nologin svc2
[root@server1 ~]# su - svc2
This account is currently not available.
```

## Lesson: l0905 | Superuser access: su and sudo

Two ways lead to root rights. Both are on the exam.

### su: become another user

`su USER` starts a shell as that user after asking for THAT user's password (root is never asked). The difference between the two forms:

- `su - USER` (or `su -l`) starts a login shell: the user's environment, PATH and home folder, as if they had logged in.
- `su USER` keeps most of your environment and your current folder. Commands may be missing from the PATH and files may land in the wrong place.
- `su -` alone means `su - root`. `su - USER -c 'command'` runs one command and returns.

```terminal
[root@server1 ~]# su student
[student@server1 root]$ pwd
/root
[student@server1 root]$ exit
exit
[root@server1 ~]# su - student
[student@server1 ~]$ pwd
/home/student
[student@server1 ~]$ exit
logout
```

### sudo: run one command as root

`sudo COMMAND` runs a command as root after asking for the user's OWN password. Nobody else needs the root password, every command is logged, and the rights can be limited to some commands. `sudo -i` opens a root login shell, `sudo -l` lists what you may do and `sudo -u USER COMMAND` runs a command as another user.

The rules are in /etc/sudoers. On RHEL it already contains this line, so members of the group wheel may run everything (with their own password):

```terminal
[root@server1 ~]# grep '^%wheel' /etc/sudoers
%wheel  ALL=(ALL)       ALL
```

So "give the user X administrator rights" is often just `usermod -aG wheel X`.

### Your own rules in /etc/sudoers.d

Never edit /etc/sudoers directly: a typing mistake can lock everybody out of sudo. Put each rule in its own file under /etc/sudoers.d (sudoers reads all files there), make the file mode 0440, and check the syntax with `visudo -c`. `visudo` alone opens /etc/sudoers in an editor and checks it before saving.

A rule reads `WHO WHERE=(AS_WHOM) WHAT`:

- `tom ALL=(ALL) ALL`: tom may run everything on all hosts as any user.
- `%ops ALL=(ALL) NOPASSWD: ALL`: members of the group ops (the % means group) may run everything without typing a password.
- `tom ALL=(ALL) /usr/bin/systemctl, /usr/bin/dnf`: tom may only run these two programs (full paths).

```terminal
[root@server1 ~]# echo '%ops ALL=(ALL) NOPASSWD: ALL' > /etc/sudoers.d/ops
[root@server1 ~]# chmod 440 /etc/sudoers.d/ops
[root@server1 ~]# visudo -c
/etc/sudoers: parsed OK
/etc/sudoers.d/ops: parsed OK
```

When a rule does not allow a command, sudo says so and the attempt goes into the log:

```terminal
[tom@server1 ~]$ sudo cat /etc/shadow
Sorry, user tom is not allowed to execute '/bin/cat /etc/shadow' as root on server1.lab.example.com.
```
