# Unit: u06 | 6. Hybrid identity and AD DS in Azure | Hybrid identity

Most companies that use Microsoft 365 or Azure keep Active Directory on premises and copy their people into **Microsoft Entra ID** (the cloud directory that used to be called Azure AD), so that one account and one password work for both. That is **hybrid identity**. This unit covers the two sync tools, the ways people's cloud sign-ins are checked, and running domain controllers as virtual machines in Azure. Harborline's tenant is `harborline.onmicrosoft.example`, and it has verified the company's public domain `harborline.example`.

## Lesson: l0601 | Microsoft Entra Connect Sync and Cloud Sync

Two Microsoft tools copy (synchronize) users, groups and contacts from AD DS to Microsoft Entra ID:

- **Microsoft Entra Connect Sync** (the older full product, once "Azure AD Connect"): installed on a domain-joined Windows Server, with its own sync engine and database (SQL Server Express LocalDB, fine up to about 100,000 objects). It can do everything: password hash sync, pass-through authentication, federation with AD FS, password writeback, device writeback, Exchange hybrid, attribute filtering and custom sync rules. One active server per tenant; others can wait in **staging mode** (next lesson).
- **Microsoft Entra Cloud Sync**: a small **provisioning agent** on one or more servers, and the configuration lives in the cloud. Several agents give high availability with nothing to fail over by hand, and it handles several forests that can't see each other (for example after a merger). It syncs every 2 minutes and supports password hash sync, but not pass-through authentication, device objects or advanced custom rules.

> Exam pattern: "lightest footprint, several disconnected forests, high availability without staging servers" = Cloud Sync. "Pass-through authentication", "federation", "device writeback" or "custom sync rules" = Connect Sync.

### Installing Connect Sync

- Run the installer on a member server (a domain controller works, but Microsoft prefers a separate server). It needs an account with **Hybrid Identity Administrator** (or Global Administrator) in the tenant and, for the express settings, an **Enterprise Admins** member on premises: the wizard creates the AD DS connector account it will use afterwards.
- **Express settings** sync the whole forest with password hash sync. **Customize** lets you choose the sign-in method, **domain and OU filtering**, and optional features.
- **OU filtering** decides which OUs are in scope. Service accounts, test users and admin accounts usually stay out. A user who leaves the scope is deleted in the cloud at the next sync.
- The service is `ADSync` (Microsoft Azure AD Sync). The **Synchronization Service Manager** shows each run; the PowerShell module is `ADSync`.

### UPN suffixes and verified domains

The cloud sign-in name comes from the on-premises **userPrincipalName**. If its suffix is a domain the tenant has **verified** (`harborline.example`), the cloud user gets the same name. If not (an internal name such as `corp.example` or `corp.local`), the user gets the tenant's initial domain instead: `bcole@harborline.onmicrosoft.example`. So before the first sync, add the public domain as a UPN suffix to the forest (unit 1) and give it to the users.

```terminal
#setup admin:connect install server=SRV1 signin=PHS ous="OU=Staff,DC=corp,DC=example"
#machine SRV1
PS C:\Windows\system32> Get-Service ADSync

Status   Name               DisplayName
------   ----               -----------
Running  ADSync             Microsoft Azure AD Sync
```

## Lesson: l0602 | Cloud sign-in: password hash sync, pass-through authentication and federation

Syncing makes the account exist in the cloud. How the **password** is checked when someone signs in to Microsoft 365 is a separate choice:

- **Password hash synchronization (PHS)**: Connect copies a hash of each password's hash to the tenant, every 2 minutes. The cloud checks passwords itself, so sign-in keeps working when the office is offline. It is the simplest method, enables leaked-credential detection in Microsoft Entra ID Protection, and Microsoft recommends turning it on even when you use another method, as a backup.
- **Pass-through authentication (PTA)**: the password stays on premises. A lightweight **authentication agent** on a server takes the sign-in request from a queue in the cloud (outbound HTTPS only, no open ports) and checks it against a DC. On-premises rules apply at once: a disabled or locked account, logon hours, an expired password. If no agent is reachable, nobody can sign in, so install **at least three agents** on different servers (the Connect server has the first one).
- **Federation** with **AD FS** (or another identity provider): the tenant sends people to your own sign-in servers (an AD FS farm plus Web Application Proxy servers in the perimeter network). Needed only for things the other methods can't do, such as certain smart card or third-party MFA set-ups; it is the most work to run, and Microsoft recommends moving to PHS or PTA.

**Seamless single sign-on** (with PHS or PTA) lets domain-joined PCs on the company network sign in to cloud apps without typing the password, using Kerberos: Connect creates the computer account `AZUREADSSOACC` in each forest, and the site `https://autologon.microsoftazuread-sso.com` is added to the browsers' Intranet zone by Group Policy. Roll over its Kerberos key regularly.

### Staging mode and sync cycles

A second Connect Sync server in **staging mode** has the same configuration and imports and syncs everything, but **exports nothing** and doesn't sync passwords. If the active server dies, you turn staging mode off on the standby (and on the old one when it returns). It is also the safe way to test a configuration change or an upgrade.

The **scheduler** runs a **delta sync** every 30 minutes. In PowerShell on the Connect server:

- `Get-ADSyncScheduler`: the interval, the next run, `SyncCycleEnabled`, `StagingModeEnabled`.
- `Start-ADSyncSyncCycle -PolicyType Delta` (changes only) or `-PolicyType Initial` (a full sync, after a configuration change).
- `Set-ADSyncScheduler -SyncCycleEnabled $false` stops the schedule for maintenance; set it back to `$true` afterwards.

```terminal
#setup admin:connect install server=SRV1 signin=PTA
#machine SRV1
PS C:\Windows\system32> Get-ADSyncScheduler | Format-List NextSyncCycleStartTimeInUTC, SyncCycleEnabled, StagingModeEnabled

NextSyncCycleStartTimeInUTC : 3/2/2026 9:30:00 AM
SyncCycleEnabled            : True
StagingModeEnabled          : False


PS C:\Windows\system32> Start-ADSyncSyncCycle -PolicyType Delta

Result
------
Success
```

@quiz
? The head office's internet link fails for a day. Which sign-in method lets people keep using Microsoft 365 from home?
+ Password hash synchronization
- Pass-through authentication
- Federation with AD FS at the head office
! With PHS the cloud checks the password itself. PTA and AD FS need servers at the office to answer.

- Password hash synchronization
+ Pass-through authentication
- Seamless single sign-on

! A configuration change needs a full (Initial) sync; Delta only looks at changed objects.
@end

## Lesson: l0603 | AD DS on Azure virtual machines

Some companies put a domain controller in Azure, next to servers that run there, so they don't depend on the VPN for every sign-in. A DC in an Azure VM is an ordinary DC, with a few Azure rules:

- **Static private IP**: set the NIC's private IP allocation to **Static** in Azure (the VM's network settings). Inside Windows, leave the adapter on DHCP: Azure always hands the VM that address. Never set a static IP inside the guest.
- **A data disk for the directory**: put the AD DS database, logs and SYSVOL on a separate **data disk** with **host caching None**, and choose that drive when you promote (`-DatabasePath`, `-LogPath`, `-SysvolPath`). The OS disk uses write caching, which can lose directory writes.
- **DNS for the virtual network**: set the VNet's **custom DNS servers** to the domain's DNS servers (the Azure DC first, an on-premises DC second) instead of Azure-provided DNS, so VMs can find the domain. VMs pick the change up when they restart or renew.
- **Sites and subnets**: create an AD site for Azure (for example `Azure`) with the VNet's address range as its subnet, and a site link to the head office, so clients in Azure use the Azure DC and replication follows the link's schedule (unit 3).
- **Connectivity**: a site-to-site VPN or ExpressRoute between the office and the VNet. Keep RDP closed to the internet; use Azure Bastion or the VPN.
- Back DCs up with Azure Backup; never restore a DC from an old disk copy. Windows Server's **VM-GenerationID** support protects a DC when a hypervisor rolls it back, but that is a safety net, not a backup method.
- Where you only need a managed domain for Azure apps and don't want to run DCs, **Microsoft Entra Domain Services** is the alternative (no Domain Admins, no schema changes).

@try
@task t1 | Hybrid identity | 10 | admin

@endtask
@task t2 | Hybrid identity | 10 | admin

@quiz
? Where do you set the static IP address of a domain controller that runs in an Azure VM?
- In Windows, with New-NetIPAddress
+ On the VM's network interface in Azure (private IP allocation Static), leaving Windows on DHCP
- In the virtual network's DHCP options
! Azure's DHCP always gives the VM its reserved address; a static address inside the guest can cut the VM off.
? Which host caching should the data disk with NTDS.dit and SYSVOL use?
+ None
- ReadOnly
- ReadWrite
! AD DS needs its writes to reach the disk; host caching None makes sure they do.
? New VMs in the VNet can't join the domain: they can't find a domain controller. What is the likely cause?
- The VMs use a static IP
+ The VNet still uses Azure-provided DNS instead of the domain's DNS servers
- The Azure site has no site link
! Joining a domain starts with DNS (the DC's SRV records); set the VNet's custom DNS servers to the domain's DNS servers.
@end
