@task t01 | AD DS | 4 | DC1
Following the AGDLP model, create the global security group **Project-{p}** in the **Groups** OU with **bcole** and **ewalsh** as members, and the domain local security group **FS-Project-{p}-Modify** in the same OU with **Project-{p}** as its only member.
@check admin | the global group and its members
group["Project-{p}"].scope == Global
group["Project-{p}"].members has bcole
group["Project-{p}"].members has ewalsh
@check admin | the domain local group holds the global group
group["FS-Project-{p}-Modify"].scope == DomainLocal
group["FS-Project-{p}-Modify"].members has Project-{p}
group["FS-Project-{p}-Modify"].allmembers has bcole
@solution DC1
New-ADGroup -Name "Project-{p}" -GroupScope Global -GroupCategory Security -Path "OU=Groups,DC=corp,DC=example"
Add-ADGroupMember -Identity "Project-{p}" -Members bcole, ewalsh
New-ADGroup -Name "FS-Project-{p}-Modify" -GroupScope DomainLocal -Path "OU=Groups,DC=corp,DC=example"
Add-ADGroupMember -Identity "FS-Project-{p}-Modify" -Members "Project-{p}"
@explain
AGDLP: Accounts go into Global groups (who people are), global groups into Domain Local groups (what they may do), and the domain local group gets the Permission on the resource. A global group can't contain a domain local group, so the nesting only works in this direction.
@endtask

@task t02 | Group Policy | 4 | admin
Create a GPO named **Finance lockdown {n}** that prohibits access to Control Panel and PC settings, link it to the **Staff/Finance** OU, and make it apply only to members of the **Finance** group. Computers must still be able to read the GPO.
@check admin | Finance users get the setting
rsop(computer=CL1, user=ewalsh).setting["NoControlPanel"] == Enabled
@check admin | other people in the OU don't
gpo["Finance lockdown {n}"].filter has Finance
gpo["Finance lockdown {n}"].filter !has "Authenticated Users"
@solution admin
gpo new "Finance lockdown {n}"
gpo set "Finance lockdown {n}" setting=NoControlPanel state=Enabled
gpo link "Finance lockdown {n}" Staff/Finance
gpo filter "Finance lockdown {n}" remove "Authenticated Users"
gpo filter "Finance lockdown {n}" add Finance
gpo perm "Finance lockdown {n}" "Domain Computers" GpoRead
@explain
Security filtering lists who gets Read and Apply. Since the MS16-072 update, user policy is read with the computer's account, so after removing Authenticated Users you must give Domain Computers (or Authenticated Users) Read, or the GPO stops applying to anyone.
@endtask

@task t03 | Networking | 4 | DC1
Both domain controllers must resolve names in the partner forest **tidewater.example**, whose DNS server is **192.168.50.10**. Configure it once, on DC1, so that it is stored in Active Directory and reaches DC2 by replication.
@check admin | DC1 and DC2 forward tidewater.example
dns(DC1).conditional["tidewater.example"] has 192.168.50.10
resolve(name=files.tidewater.example, server=DC2) == 192.168.50.20
@check admin | a client gets the answer
resolve(client=CL1, name=files.tidewater.example) == 192.168.50.20
@solution DC1
Add-DnsServerConditionalForwarderZone -Name tidewater.example -MasterServers 192.168.50.10 -ReplicationScope Domain
@explain
A conditional forwarder sends queries for one domain to the servers you name. Stored in Active Directory with the Domain scope, it replicates to every DC that runs DNS in the domain; a file-backed one would exist on DC1 only.
@endtask

@task t04 | Virtualization | 4 | HV1
The training team will run Hyper-V inside the virtual machine **LAB-HOST**, and its nested VMs need network access through the VM's adapter. Prepare LAB-HOST and start it.
@check admin | nested virtualization is on
vm["LAB-HOST"].nested == Yes
vm["LAB-HOST"].dynamic == No
@check admin | its nested VMs can reach the network and it runs
vm["LAB-HOST"].spoofing == On
vm["LAB-HOST"].state == Running
@solution HV1
Set-VMMemory -VMName LAB-HOST -DynamicMemoryEnabled $false
Set-VMProcessor -VMName LAB-HOST -ExposeVirtualizationExtensions $true
Set-VMNetworkAdapter -VMName LAB-HOST -MacAddressSpoofing On
Start-VM -Name LAB-HOST
@explain
Nested virtualization needs the VM switched off while you expose the processor's virtualization extensions, and it doesn't work with dynamic memory. MAC address spoofing lets the nested VMs' traffic, with their own MAC addresses, leave through the outer VM's adapter (the alternative is NAT inside the VM).
@endtask

@task t05 | File and storage | 4 | FS1
The Finance team reports that they can open but not save files in **\\FS1\Finance**. The NTFS permissions are correct. Fix the share so that members of **Finance** can change files there, without giving anyone else access.
@check admin | Finance can change files over the network
access(user=ewalsh, path="\\FS1\Finance") == Modify
access(user=fhaddad, path="\\FS1\Finance").rights has Write
@check admin | others still can't
access(user=bcole, path="\\FS1\Finance") == "No access"
@solution FS1
Grant-SmbShareAccess -Name Finance -AccountName "CORP\FS-Finance-Modify" -AccessRight Change -Force
@explain
Over the network the more restrictive of the share and NTFS permissions wins. The share gave Everyone only Read, so Finance's NTFS Modify was cut down to read. Granting Change on the share to the group that already has Modify on NTFS fixes it; NTFS still keeps everyone else out.
@endtask

@case cs1 | Fairwind Ferries
## Overview
Fairwind Ferries (a made-up company) runs passenger ferries from a head office in Halifax and two harbour offices, Dartmouth and Sydney. It has 400 staff and an IT team of four.

## Existing environment
The Active Directory forest fairwind.example has one domain and two domain controllers, both in the head office, in the default site. DC-HFX1 holds all the operations master roles. The harbour offices connect to the head office over slow VPN links and have no servers; their PCs get addresses from a router there. All servers run Windows Server 2022. Users sign in to Microsoft 365 with separate cloud accounts.

## Requirements
- Each harbour office gets a read-only domain controller that also runs DNS. Sign-ins at a harbour office must use the local DC when it works.
- Replication to the harbour offices must happen at most every 30 minutes, and only over the VPN links.
- Users must sign in to Microsoft 365 with their Active Directory user name and password. Passwords must not be checked by an on-premises server during sign-in, and sign-in must keep working if the head office is offline.
- Each harbour office gets its own DHCP server; if one fails, the head office's DHCP server must take over its clients.
- The PCs in the harbour offices' crew rooms are shared: anyone who signs in to them must get the same locked-down desktop, whatever OU their account is in.

## Technical constraints
Keep the number of servers and the administrative effort low.
@endcase
