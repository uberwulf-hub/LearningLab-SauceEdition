@task t01 | Compliance | 4 | portal
Create a compliance policy for Windows 10 and later called **Windows baseline {n}**. It must require BitLocker and Secure Boot and a minimum OS version of **10.0.26100**. Devices that fail it must be marked noncompliant **1 day** after they fail. Assign it to the **Windows devices** group.
@check portal | the policy has the right settings
compliance["Windows baseline {n}"].platform == "Windows 10 and later"
compliance["Windows baseline {n}"].bitlocker == Require
compliance["Windows baseline {n}"].secureBoot == Require
compliance["Windows baseline {n}"].minOs == 10.0.26100
compliance["Windows baseline {n}"].noncompliantDays == 1
@check portal | it is assigned to Windows devices
compliance["Windows baseline {n}"].include has "Windows devices"
@solution portal
create compliance name="Windows baseline {n}" platform="Windows 10 and later" bitlocker=Require secureBoot=Require minOs=10.0.26100 noncompliantDays=1
assign compliance "Windows baseline {n}" "Windows devices"
@explain
Devices > Compliance > Create policy, platform Windows 10 and later. BitLocker and Secure Boot are under Device Health, the minimum OS version under Device Properties, and the grace period is the first action under Actions for noncompliance ("Mark device noncompliant", 1 day after noncompliance). A policy does nothing until it is assigned.
@endtask

@task t02 | Identity | 3 | portal
Create a security group called **Sales staff {n}** whose members are, automatically, every user whose department is **Sales**.
@check portal | a dynamic user group with a department rule
group["Sales staff {n}"].membership == "Dynamic user"
group["Sales staff {n}"].rule contains department
@check portal | it holds the Sales people and nobody else
group["Sales staff {n}"].members has jordan
group["Sales staff {n}"].members has priya
group["Sales staff {n}"].members !has sam
@solution portal
create group name="Sales staff {n}" type=Security membership="Dynamic user" rule="(user.department -eq \"Sales\")"
@explain
Users and groups > Groups > New group: Security, membership type Dynamic user, and a rule on user.department. Dynamic groups need Microsoft Entra ID P1 licences. A rule uses either user properties or device properties, never both.
@endtask

@task t03 | Apps | 4 | portal
Add 7-Zip to the tenant as a Windows app (Win32) from the package **7z2301-x64.intunewin** (its setup file is 7z2301-x64.exe, which installs silently with **/S** into C:\Program Files\7-Zip). Use a file detection rule for 7z.exe in that folder. Make it **required** for the **Sales** group, and make sure it is installed on **RB-LT-001**.
@check portal | the app is a Win32 app with a working detection rule
app["7-Zip"].type == "Windows app (Win32)"
app["7-Zip"].required has Sales
@check portal | RB-LT-001 has it installed
device["RB-LT-001"].app["7-Zip"] == Installed
@solution portal
create app name=7-Zip type="Windows app (Win32)" publisher="Igor Pavlov" package=7z2301-x64.intunewin installCmd="7z2301-x64.exe /S" uninstallCmd="\"C:\Program Files\7-Zip\Uninstall.exe\" /S" installBehavior=System arch=x64 minOs="Windows 10 1607" detect=File detectPath="C:\Program Files\7-Zip" detectName=7z.exe
assign app 7-Zip Sales intent=required
remote sync RB-LT-001
@explain
Apps > All apps > Add > Windows app (Win32). The install command must be silent (the installer can't wait for someone to click), install behavior System because it writes to Program Files, and the detection rule must find what the installer leaves behind. A Required assignment installs at the device's next check-in: Sync makes it check in now. Jordan, RB-LT-001's user, is in Sales.
@endtask

@task t04 | Protection | 4 | portal
Manage the local administrator password of every Windows device with Windows LAPS, backed up to **Microsoft Entra ID**, with a password age of **{age} days**. Make sure **RB-LT-002** already has a managed password.
@check portal | Entra LAPS is on for the tenant
tenant.lapsEnabled == Yes
@check portal | a LAPS policy backs up to Microsoft Entra ID
count(laps, backup="Backup the password to Microsoft Entra ID only") >= 1
@check portal | RB-LT-002's password is managed and backed up
device["RB-LT-002"].laps == On
device["RB-LT-002"].laps.backup == "Microsoft Entra ID"
@solution portal
tenant lapsEnabled=Yes
create laps name="LAPS for Windows" backup="Backup the password to Microsoft Entra ID only" ageDays={age}
assign laps "LAPS for Windows" "Windows devices"
remote sync RB-LT-002
@explain
Two switches are needed: "Enable Microsoft Entra Local Administrator Password Solution (LAPS)" in the Microsoft Entra device settings, and a LAPS policy (Endpoint security > Account protection) with the backup directory set to Microsoft Entra ID. Without the tenant switch, the device can't back the password up and the policy reports an error.
@endtask

@case cs1 | Lakeshore Dental Clinics
## Overview
Lakeshore Dental Clinics (a made-up company) has a head office and four clinics, and 140 staff. Every member of staff has a Microsoft 365 E3 licence, and the IT team of two manages devices with Microsoft Intune.

## Existing environment
The on-premises Active Directory domain lakeshore.local is synchronised to Microsoft Entra ID. The office PCs run Windows 10 Pro 22H2; they are hybrid joined and were enrolled in Intune through Group Policy. Some of them have a TPM 1.2 chip. Each clinic has two shared front-desk PCs. Clinicians read their email on their own iPhones, which are not enrolled. New laptops come from a reseller that can register them for Windows Autopilot.

## Requirements
- Clinicians set up their new laptops themselves, at home, without help from IT. The laptops join Microsoft Entra ID only, and clinicians must not be local administrators.
- The front-desk PCs show only the booking website, full screen, in Microsoft Edge.
- Email on phones is allowed only in Microsoft Outlook with company data protected. Phones must not be enrolled.
- Every Windows device is encrypted without asking the user anything, and the recovery keys are kept in the cloud.
- The office PCs move to Windows 11, version 24H2, before the end of the year. PCs that can't run Windows 11 stay on Windows 10 until they are replaced.

## Technical constraints
Keep administrative effort low. Licences can't change.
@endcase

@choice c1 | Deployment | 1 | case=cs1

- Self-deploying mode, Microsoft Entra joined
+ User-driven mode, Microsoft Entra joined, user account type Standard
- User-driven mode, Microsoft Entra hybrid joined

! The clinician signs in during setup (user-driven), the laptop must be Entra joined only (not hybrid, which would also need the office network or a VPN and a Domain Join profile), and the profile's user account type Standard keeps the clinician from being an administrator. Self-deploying mode is for devices without a user, such as kiosks.

! A kiosk profile in single-app mode runs one app full screen; with Microsoft Edge as the app it opens the given start URL. The other profiles don't lock a PC to one app.

@yesno c4 | Protection | 3 | case=cs1
For the encryption requirement, decide whether each statement is true.
Y A disk encryption policy that requires device encryption, sets Allow Warning For Other Disk Encryption to Disabled and allows standard user encryption can turn BitLocker on without prompting the clinicians.
N Requiring a startup PIN with the TPM keeps the encryption silent.

@choice c5 | Updates | 1 | case=cs1
What should you use to move the office PCs to Windows 11, version 24H2?
- An update ring with the feature update deferral set to 0 days
+ A feature updates policy for Windows 11, version 24H2, assigned to a group of the office PCs
- A quality updates policy that expedites the newest update
- A driver updates policy with automatic approval
! A feature updates policy names the version to move to and keeps devices there. Windows Update offers Windows 11 only to PCs that meet its hardware requirements, so the PCs with a TPM 1.2 aren't upgraded and stay on Windows 10, version 22H2, the last Windows 10 feature update. Rings control timing (deferrals, deadlines), not which version.

@choice q05 | Compliance | 1
A compliance policy marks devices noncompliant 3 days after they fail. Conditional Access requires a compliant device. A device fails the policy today. What happens when its user signs in to Office 365 tomorrow?
+ The sign-in succeeds: the device is in its grace period, which counts as compliant
- The sign-in is blocked: the device failed a setting

! Until the grace period ends, the device's state is "In grace period", and Conditional Access treats it as compliant. After 3 days it becomes Not compliant and the sign-in is blocked.

@choice q09 | Configuration | 1

@choice q12 | Monitoring | 1
Jordan is leaving Riverbend. His own iPhone is enrolled. You must remove company apps, data and settings and keep his personal photos. Which remote action?
- Wipe
+ Retire
- Delete
- Fresh Start
! Retire removes what the company put on the device and takes it out of management, and leaves personal data. Wipe resets the whole device. Delete removes the device's record from Intune (on Windows and iOS it also sends a retire), so it isn't the action for keeping a clean, managed handover.
